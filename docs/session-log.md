## 2026-08-06 (3) — passwords over 72 bytes were silently truncated by bcrypt

Continuation of the same session as the two entries directly below. The third survey pass mentioned at the end of entry (2) came back with one genuine finding, independently re-verified before acting (not taken on trust): `packages/schema/src/auth.ts`'s `signupSchema`/`acceptInviteSchema` enforced only a minimum password length (`.min(8)`), no maximum, and both `POST /auth/signup` and `POST /invites/:token/accept` hash the raw password with `bcrypt.hash(password, 12)` via `bcryptjs` — which silently truncates its input at 72 bytes, both when hashing and when comparing.

Reproduced directly before touching anything: `bcrypt.hash("A".repeat(72) + "-suffix-one", 12)` then `bcrypt.compare("A".repeat(72) + "-DIFFERENT-SUFFIX", hash)` returns `true` — two different passwords sharing the same first-72-byte prefix authenticate identically. **Before:** a user who picks a long passphrase (a genuine security best practice, e.g. one generated by a password manager) has their actual password entropy silently capped at 72 bytes with zero indication anywhere in the UI or API. **After:** `signupSchema`/`acceptInviteSchema` reject a password over 72 UTF-8 bytes with a clear `400`, turning the invisible truncation into an explicit validation error.

**Shipped:** added a shared `passwordSchema` in `auth.ts` (`.min(8)` plus a byte-length `.refine()` capped at 72, measured with `TextEncoder` rather than Node's `Buffer` since `packages/schema` is also imported — currently type-only, but the package is meant to be environment-agnostic — by the web bundle), used by `signupSchema` and `acceptInviteSchema`. `loginSchema` deliberately untouched since it only compares against an already-stored hash and doesn't need the cap. Added `apps/api/tests/passwordLength.test.ts`: reproduces the underlying `bcryptjs` truncation directly, then asserts the schema rejects 73 bytes, accepts exactly 72, rejects by UTF-8 byte length rather than character count (40 "é" characters = 80 bytes — verifies the fix isn't fooled by multi-byte characters), and that `acceptInviteSchema` shares the bound. Added one integration test to `apps/api/tests/auth.test.ts` proving `POST /auth/signup` with a 73-character password now 400s instead of silently succeeding with a truncated password. Verified with `pnpm typecheck` (clean), `pnpm test` (88/88, was 82), `pnpm build` (clean). Merged: [PR #16](https://github.com/akkinallani/assay/pull/16) via squash merge, CI green before merge.
